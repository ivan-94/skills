# 技能审查员

从智能体的角度审查技能：智能体需要先判断是否加载它，加载后还要知道怎么行动。默认只做只读审查；只有用户明确要求修改文件时，才实际编辑技能。

## 输入

- 解析用户指定的技能路径、名称或目录。目标不清楚时，只问一个直接问题。
- 先读 `SKILL.md`。
- 只有在需要判断行为时，才读取它直接链接的一层引用文件。
- 如果技能位于一个包含技能列表或 README 索引的仓库，只为了判断触发重叠、命名和放置位置而检查这些文件。

## 审查视角

检查这个技能是否真的能让智能体行为更好：

1. 触发质量：YAML 前置信息里的 `description` 说明技能做什么、何时使用，并足够具体，能减少误触发和漏触发。
2. 范围和目标：技能有明确任务、边界和可识别的完成状态。
3. 行为契约：必要动作、可选动作、停止条件、读写权限在关键处说清楚。
4. 操作路径：冷启动时前三步可执行；必要输入、文件、命令和产物可发现。
5. 冲突和优先级：内部指令、系统/开发者指令、仓库指令、相邻技能之间没有矛盾。
6. 冗余和上下文成本：重复解释、泛泛建议、庞大引用材料应删除、合并，或通过渐进披露后置。
7. 歧义和弱引导：`考虑`、`处理`、`确保` 之类的模糊动词，需要有具体检查或决策规则支撑。
8. 组合关系：说明什么时候使用其他技能，什么时候不要使用，以及交接产物如何保留来源上下文。
9. 验证方式：需要验证时说明怎么验证，不要求虚假或无法完成的检查。
10. 输出可用性：期望输出格式足够具体，下游智能体或人类可以直接行动。

## 严重级别

只报告有明确智能体失败模式的问题。

- `P0`：技能可能导致危险、破坏性或明显错误的行为，或核心场景无法可靠触发。
- `P1`：技能很可能误导智能体、与其他指令冲突，或让核心流程保持歧义。
- `P2`：技能基本可用，但存在有实际成本的可维护性、上下文成本、验证或下游使用问题。

不要报告纯措辞偏好、夸奖，或没有具体失败模式的猜测。

## 流程

1. 冷启动测试：只看名称和 frontmatter，列出可能触发词、可能漏掉的触发词、可能误触发的触发词。
2. 执行模拟：读完正文后，写出智能体会采取的前三个动作。如果写不出来，这本身就是问题。
3. 冲突检查：对照技能内部、链接文件、相邻技能，以及当前任务适用的仓库级指令。
4. 压缩检查：找出应删除、合并，或移动到一层引用文件的内容。
5. 修订检查：每个发现都给出能修复行为的最小替换文本。
6. 如果用户明确要求修复技能，做聚焦编辑，然后重新审查改过的部分。

## 输出格式

先列发现，按严重级别排序：

````text
[P1] 标题 - path:line
问题：...
智能体失败模式：...
修复：...
替换文本：
```md
...
```
````

发现之后再包含：

- `建议结构`：只有技能需要结构调整时才写。
- `未发现问题`：没有可行动问题时写，并说明剩余审查限制。
- `已应用变更`：只有实际编辑文件时才写。

保持审查紧凑。优先给精确替换段落，不给泛泛建议。
